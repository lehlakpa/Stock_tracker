## Firebase setup and deployment

The Firebase apps and local configuration have been created. Backend deployment, authentication settings, billing/Identity Platform activation and initial-admin creation are project-owner steps. Complete these before using real inventory.

1. Select **stocktracker-f8f91** in Firebase console and create a **Cloud Firestore Standard database** in production mode if absent. Choose the intended data region.
2. Enable **Authentication → Sign-in method → Email/Password**.
3. Upgrade Authentication to **Identity Platform**, and use a billing plan supporting Cloud Functions. Blocking functions are essential: Firestore rules cannot prevent calls to Firebase Auth's public signup API.
4. Install Node.js 22.12 or newer within Node 22, Firebase CLI, and FlutterFire CLI. Cloud Functions uses Node 22.
5. Bootstrap the first admin using the instructions below, then deploy the backend before allowing app access.

```powershell
npm install -g firebase-tools
firebase login
dart pub global activate flutterfire_cli
dart pub global run flutterfire_cli:flutterfire configure --project=stocktracker-f8f91 --platforms=android,web,windows --android-package-name=com.example.stock_tracker --out=lib/firebase_options.dart --yes
npm --prefix functions ci
firebase deploy --project stocktracker-f8f91 --only firestore:rules,firestore:indexes,functions
```

`firebase.json` contains rules, indexes, functions and emulator configuration. `.firebaserc` selects the supplied project. Deployment creates:

- `requireAdminInvitation`: rejects Auth account creation without an unexpired request written by an active admin; consumes it transactionally.
- `checkAccountOnSignIn`: rejects inactive accounts and updates `lastLogin` on the trusted server. Newly provisioned accounts may temporarily lack a profile; rules grant them no application-data access.
- `aggregatePurchase`: maintains admin-only totals with a processing ledger, so repeated event delivery does not double-count revenue.

Verify **before-create** and **before-sign-in** hooks in Authentication settings after deployment. Before-create must remain enabled. Confirm that an uninvited signup is rejected before distribution. Auth and Firestore are separate services: failed profile writes trigger deletion of the secondary account, and failed cleanup reports the recovery required.

## Create the first admin

A trusted Firebase project operator must create the initial admin; clients cannot bootstrap their own role. Use the included Admin SDK script before enabling the before-create hook, then deploy/enable the hook immediately. Run one bootstrap operation at a time.

Install Google Cloud CLI and authenticate Application Default Credentials with an account authorized for Firebase Authentication and Firestore. Firebase CLI login alone does not authenticate the Admin SDK. No password is stored in source or command-line arguments.

```powershell
gcloud auth application-default login
gcloud auth application-default set-quota-project stocktracker-f8f91
$adminEmail = Read-Host 'Admin email'
$adminName = Read-Host 'Admin name'
$adminPhone = Read-Host 'Admin phone'
$adminBranch = Read-Host 'Admin branch'
$securePassword = Read-Host 'Admin password (at least 8 characters)' -AsSecureString
$env:STOCKFLOW_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
try {
  node functions/bootstrap-admin.js stocktracker-f8f91 $adminEmail $adminName $adminPhone $adminBranch
} finally {
  Remove-Item Env:STOCKFLOW_ADMIN_PASSWORD
}
```

The script refuses if an admin profile already exists and deletes the new Auth user if its profile cannot be written. Alternatively, create the initial Auth user through Firebase console and create `users/{uid}` with these fields, using the UID from Authentication. Never loosen security rules to bootstrap an admin.

| Field | Value/type |
| --- | --- |
| uid | Actual Auth UID, string |
| name, email, phone, branch | Actual account details, strings |
| role | `admin` |
| isActive | boolean `true` |
| createdAt | Firestore timestamp |
| lastLogin | `null` initially; server updates on sign-in |

Sign in, then use **Overview → menu → Staff management → Register staff / Register admin**. The admin writes a five-minute provisioning request, creates the user with a secondary Firebase app/Auth instance, writes the profile with the main admin's Firestore session, then signs out and deletes the secondary app. The main admin stays signed in. New users should reset their temporary password.

## Architecture and behavior

The requested `constants`, `models`, `services`, `providers`, `screens` and `widgets` structure is retained. `main.dart` initializes Firebase and assembles the app. Extra reusable forms and state/transition components live in `widgets`.

- Auth state plus live profiles select login, admin/staff dashboard, inactive account or missing-profile error. Invalid roles receive access denied.
- Session-scoped Providers and a nested Navigator are discarded on logout, role change or deactivation, including protected pages and sheets. Listeners are canceled and data is not carried into a different user's session.
- Admins see totals, reports, all activity, registration and staff management. Staff see inventory, available quantities, buyers and their own stock history; their UI never displays aggregate sales/income or user-management controls.
- Inventory, buyers, history, notifications, staff profiles and financial totals use Firestore streams. Provider handles auth/stock/buyer loading and operation errors. Firebase failures use custom SnackBars.
- Stock forms, buyer forms, filters, notification details and staff details use `CustomDraggableSheet`, its supplied ScrollController, snapping and keyboard-aware expansion. Saving forms prevent dismissal; successful mutations close them and failures retain input.
- Material 3, shared colors/sizes, 300 ms ease-in-out transitions, AnimatedSwitcher states, animated filters/navigation, fade/slide appearance and product Hero transitions are included.
- Low-stock changes create a private notification for the operator; the live low-stock count is shared with active users. Notifications are in-app records, not FCM push notifications.

## Data and consistency

The required collections and fields are modeled in Dart and validated in `firestore.rules`: `users`, `products`, `buyers`, `stock_updates`, `notifications`.

Additional supporting records:

- `products/{id}.lastUpdateId` links each product mutation to a new, atomically written history entry.
- `account_requests/{normalizedEmail}` holds short-lived admin-only provisioning authorization, consumed by the hook and removed after provisioning.
- `reports/summary` contains admin-only `totalSales` (units), `totalIncome` (gross revenue), `purchaseCount`, `updatedAt`.
- `reports/summary/processed/{buyerId}` is the server-only aggregation deduplication ledger.

Quantities satisfy `remainingQuantity = addedQuantity - soldQuantity`. Manual adjustments change added and remaining quantities by the same signed delta; downward corrections reduce net stock received. Purchases increment sold quantity and reduce remaining quantity. Transactions read current stock and price, reject overselling, and write buyer/product/history together. An open purchase form retains one operation ID so retrying a committed purchase cannot reduce stock twice.

Buyer/history entries are immutable even for client admins; reports are server-written. Admins access all requested operations and records but cannot bypass accounting invariants or change their own role. Product deletion and historical purchase editing are not exposed; use trusted migrations for historical corrections. Existing data needs the listed schema before importing.

Report events may briefly lag purchases. Existing purchases imported before deploying the aggregate function need a trusted report backfill. Amounts use the requested numeric fields; choose a business currency convention before entry. No currency conversion occurs.

### Financial confidentiality boundary

Rules deny staff reads of `reports/**`; staff cannot write reports or access report pages. However, staff can read every buyer's `totalAmount` and every product's `soldQuantity` and prices, as requested. A client can calculate totals from those records. Firestore cannot redact individual document fields. Strict secrecy of underlying amounts requires changing the requested schema/access: put financial fields in admin-only documents and expose a separate operational view to staff. This implementation preserves the requested fields/read permissions and does not claim to prevent inference of totals.

## Security and verification

Rules require active authenticated profiles for application data, bind actor identities to profiles, prevent self-promotion, validate types/non-negative quantities, and use `getAfter()` to check atomic product/buyer/history consistency. Deactivation blocks server access and closes the staff UI through its profile stream. Information already downloaded by a malicious client cannot be remotely erased.

Composite indexes in `firestore.indexes.json`:

- `stock_updates`: `updatedByUid ASC`, `createdAt DESC`.
- `notifications`: `recipientUid ASC`, `createdAt DESC`.

Other queries use default single-field indexes. Wait for indexes to finish building after deployment.
